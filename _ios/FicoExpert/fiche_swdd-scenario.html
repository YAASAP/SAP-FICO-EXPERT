Le workflow flexible est une couche de paramétrage posée sur un moteur standard : on ne réécrit pas le moteur, on configure des conditions, des agents et une activation. Savoir à quel niveau agir évite 90 % des erreurs.

Transaction SWDD_SCENARIO (ancien nom SWB_PROC, obsolète) · règles d'agents PFAC · activation SPRO / SWU3 · suppression de version PFWS · runtime SWIA, SWI1, SWI2_DIAG

1. Comprendre le principe

Chaque scénario (WS…) référence une classe ABAP standard (par exemple CL_MM_PUR_PO_FLEX_WFL pour les commandes d'achat) et expose des points de configuration : conditions, règles d'agents, activation par type de document. Quand un comportement semble incohérent, identifie d'abord le niveau concerné :

NiveauOù
ScénarioSWDD_SCENARIO
Activation par type de documentSPRO, contrôle SWU3
Modèle de workflow sous-jacentPFTC / PFWS
ExécutionSWIA / SWI1
À retenirUn paramétrage correct à un niveau ne compense pas une erreur à un autre niveau.

4. Conditions : syntaxe et pièges

L'éditeur s'ouvre par double-clic sur une étape Condition ou sur les préconditions d'un bloc flexible. Il combine opérateurs, connecteurs And/Or/Not et une case Not qui inverse la ligne.

OpérateurSens
EXÉgal
NXDifférent
NENon égal, indisponible sur les domaines à valeurs fixes
Piège : domaine à valeurs fixesSur un champ comme le code de blocage paiement (DZLSPR), l'opérateur NE n'est pas proposé. Combine = avec la case Not cochée.
Not   Express.1            Op.   Express.2
not   &PAYMENT_BLOCK&      =     Y
→ NOT(&PAYMENT_BLOCK& = Y) : vrai pour tout motif différent de Y

5. Démarrage ou étape : le piège n°1

Où poser la conditionEffet
Conditions de démarrage du scénarioEmpêche l'instanciation : aucune trace en SWIA si elle est fausse
Condition d'une étape ou précondition d'un blocLe workflow existe déjà ; seule l'étape est sautée ou en attente, visible en SWIA quoi qu'il arrive
SymptômeDes instances apparaissent en SWIA alors qu'une condition était censée bloquer un motif : elle a presque sûrement été posée sur l'étape, pas sur le démarrage.

CritèreType F : fonction ABAPType R : responsabilités

Cas d'usageRésolution croisant société, montant, centre de coûtApprobateurs nominatifs fixes

Règle empiriquePour des approbateurs fixes et connus, choisis le type R : un développement ABAP pour une logique qui n'a rien de dynamique est un surcoût inutile.

7. Activation par type de document

  1. SPRO → Gestion des matériaux → Achats → Commande → Workflow flexible pour commandes (ou recherche « Flexible Workflow »).
  2. Nœud Activate Flexible Workflow for Document Types : vérifie que chaque type de document concerné référence le bon scénario.
  3. SWU3 : le point « Classify Flexible Workflow scenario tasks as general » doit être vert. Un KO empêche le déclenchement même si le scénario est correct.
  4. Transporte ce paramétrage SPRO, distinct du transport de la définition du scénario (objet R3TR WFDS).

8. Tuile Fiori « Manage Workflows »

  1. Accès par la tuile « Manage Workflows » du lanceur, ou l'URL /sap/bc/ui5_ui5/sap/mmpur_s4_wf_ui/index.html pour les commandes.
  2. Renseigne la classification d'étape de toute nouvelle étape d'approbation (onglet Pilotage). Sans elle : avertissement au contrôle syntaxique et risque de non-affichage.
  3. Teste la remontée avec un utilisateur couvert par la règle d'agent.
  4. Note la tuile et son URL dans la fiche de paramétrage pour le support N1/N2.

9. Cycle de vie des versions

StatutSensImpact
Nouveau, sauvegardéBrouillonAucun
ActifActivé par Scénario → ActivationEffectif pour toute nouvelle instance

Les instances déjà démarrées restent sur leur version d'origine : aucune migration automatique. Une migration forcée est possible via SWIA/SWPR, mais elle peut réordonner ou invalider des étapes déjà franchies : valide-la avec le métier.

Supprimer une version

SWDD_SCENARIO ne propose aucune suppression de version. Passe par le modèle de workflow :

  1. /nPFWS, saisis l'ID du workflow (ex. 90000003 pour WS90000003).
  2. Modifier (le bouton reste grisé en affichage).
  3. Traiter → Supprimer versions…, sélectionne la ou les versions, valide.
Impossible si la version estactive, en cours d'utilisation (instance ouverte), ou la dernière restante. Bouton grisé malgré tout : vérifie un verrou (SM12) ou l'autorisation S_WF_WI. Des brouillons jamais activés peuvent rester sans risque.

  1. Identifie le scénario exact.
  2. SWI1 sur le work item en erreur : lis le log complet.
  3. Bloc flexible en attente prolongée ? Vérifie d'abord si la condition attendue n'est simplement pas remplie.
  4. Instances malgré une condition censée les bloquer ? Contrôle le niveau de la condition (§5).
  5. Statut document et work item désynchronisés ? Pense à une facture débloquée directement hors workflow.

11. Checklist de paramétrage

  1. Crée une nouvelle version (Scénario → Définir version) au lieu d'écraser une version active.
  2. Place les étapes par glisser-déposer.
  3. Paramètre les conditions au bon niveau (§5).
  4. Crée ou affecte les règles d'agents PFAC, type F ou R (§6).
  5. Renseigne la classification d'étape des étapes d'approbation.
  6. Contrôle de syntaxe (Ctrl+F2) : traite les erreurs, analyse les avertissements.
  7. Active la version, hors heures de forte activité si le processus est critique.
  8. Vérifie l'activation par type de document et SWU3 (§7).
  9. Teste la remontée Fiori avec un utilisateur de test (§8).
  10. Transporte (SE09/SE10, R3TR WFDS) et vérifie le package ; $TMP n'est pas transportable.
  11. Recette, puis documente dans une spécification de paramétrage.

12. Pièges fréquents

  • Une condition d'étape ne bloque jamais le démarrage.
  • Domaine à valeurs fixes : = avec Not, pas de NE.
  • Approbateurs fixes : type R plutôt que F.
  • Bloc flexible long en SWIA : souvent normal.
  • Coexistence de versions : aucune migration automatique.
  • Suppression de version : PFWS, jamais SWDD_SCENARIO.
